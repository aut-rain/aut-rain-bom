## 1. 项目定位与维护边界

项目坐标为 `io.github.aut-rain:aut-rain-bom`，打包类型为 `pom`。源码仓库：[aut-rain/aut-rain-bom](https://github.com/aut-rain/aut-rain-bom)。

本项目统一管理第三方依赖版本，不包含业务代码，不依赖使用方工程。导入 BOM 只引入依赖管理规则，不会自动添加所有依赖。

- 依赖管理位于 [pom.xml](../pom.xml) 的 `dependencyManagement`。
- `properties` 集中声明本项目直接使用的版本变量。
- `release` profile 只负责本项目的签名与发布。
- `scope=import` 不会把 BOM 的属性、构建插件或 profile 继承到使用方。使用方需要自行配置 Java 编译版本和 Spring Boot 打包插件。
- 消费方仅声明与 BOM 同名的版本属性，通常不能覆盖被导入 BOM 中的版本。需要覆盖时，应在消费方 `dependencyManagement` 显式管理对应依赖，并记录原因。

## 2. 版本策略

已发布版本不可覆盖。每次改变对外依赖基线，都发布一个新版本。

| 变更 | 建议版本 | 说明 |
| --- | --- | --- |
| 兼容性修复、安全补丁、兼容的依赖升级 | `1.0.1` | 仍须验证使用方 |
| 新增一组受管理依赖且保持兼容 | `1.1.0` | 记录新增坐标与适用范围 |
| Spring Boot 大版本切换、Java 最低版本提升或破坏性调整 | `2.0.0` | 提供迁移说明 |
| 仅修改文档 | 不发布 Maven 版本 | 提交文档即可 |

版本号表达的是本 BOM 的兼容性，不必与任意单个依赖的版本号相同。实际存在不兼容变化时，应按破坏性变更处理。

正式发布使用固定版本，例如 `1.0.1`。不要将 `SNAPSHOT`、版本范围或 `LATEST` 作为正式依赖基线。当前工作流用于正式发布，未配置快照发布流程。

## 3. 每次迭代如何修改

### 3.1 确认修改起点

在独立仓库目录执行：

```powershell
git status --short --branch
git switch main
git pull --ff-only origin main
git switch -c codex/bom-1.0.1
```

先处理已有未提交工作，避免把无关修改混入本次发布。以下以 `1.0.1` 为示例，实际操作需替换为本次版本。

### 3.2 调整依赖

1. 明确升级原因：漏洞修复、兼容性修复、功能需要或生命周期维护。
2. 阅读目标依赖的发行说明，并确认 Java、Spring 与中间件兼容要求。
3. 修改 `pom.xml` 中实际被引用的版本属性；新增依赖时同时添加对应管理条目。
4. 将项目顶层 `<version>` 更新为本次版本，同步 README 的使用示例。
5. 记录升级前后版本、验证结果及使用方需要调整的配置。

维护重点：

- Spring Boot、Spring Cloud、Spring Cloud Alibaba 应按官方兼容矩阵组合升级，不分别追逐最新版本。
- 调整上游 BOM 导入顺序可能影响重复依赖的最终版本，必须比较 effective POM。
- 本项目显式管理的条目可能覆盖上游 BOM 的选择。升级 Spring Boot 后，要重新审视这些覆盖是否仍有必要。
- 仅新增一个属性不会自动锁定对应依赖版本。应确认它被管理条目引用，或明确交给上游 BOM 管理。
- Dubbo、AWS SDK 等包含多个组件，调整时检查组件之间是否版本一致。
- 不在通用 BOM 中增加某个业务工程的内部模块或私有仓库依赖。

### 3.3 记录变更

每次发布在 GitHub Release 描述或 `docs/releases/版本号.md` 中记录以下信息：

```markdown
# 1.0.1

发布日期：YYYY-MM-DD
发布提交：完整 commit SHA
发布标签：v1.0.1

## 依赖变化

| 坐标或组件 | 原版本 | 新版本 | 原因 |
| --- | --- | --- | --- |
| 示例组件 | 原版本 | 新版本 | 升级原因 |

## 兼容范围与迁移

Java / Spring 基线、破坏性变化、使用方操作。

## 验证结果

实际执行的命令、使用方验证范围、已知限制。
```

## 4. 发布前验证

### 4.1 Maven 模型检查

在 BOM 仓库中执行：

```powershell
mvn --batch-mode --no-transfer-progress validate
mvn --batch-mode --no-transfer-progress help:effective-pom "-Doutput=target/effective-pom.xml"
git diff --check
```

检查 effective POM 中的目标依赖版本、重复管理条目和未解析占位符。不要激活 `release` profile 来导出供分享的 effective POM：当前签名配置引用口令环境变量，可能把敏感值展开到文件中。

`validate` 成功只说明 Maven 模型可解析，不代表所有受管理依赖均可下载，也不代表运行时兼容。

### 4.2 使用方验证

在 BOM 仓库执行 `mvn install`，将待发布 POM 安装到本地。该命令不激活 `release`，不会上传到 Central。

在一个独立示例工程或指定的使用方测试分支中导入待发布版本，并按需添加依赖。然后在使用方执行：

```powershell
mvn --batch-mode --no-transfer-progress dependency:tree "-DoutputFile=dependency-tree.txt"
mvn --batch-mode --no-transfer-progress clean verify
```

比较升级前后的依赖树，排查多版本冲突、显式版本覆盖和不兼容的传递依赖。按变更范围验证应用启动、数据库访问、Redis、消息、RPC、认证或对象存储等实际功能。

纯 BOM 没有运行时代码，单独运行它的 `test` 或查看它的依赖树不能替代使用方验证。记录实际测试过的能力，不把未执行的集成验证标记为通过。

## 5. 正式发布

### 5.1 发布配置

当前 [publish.yml](../.github/workflows/publish.yml) 支持两种触发方式：推送 `v*` 标签，以及手动 `Run workflow`。发布命令为：

```text
mvn --batch-mode --no-transfer-progress -Prelease deploy
```

项目使用 Central Portal，`publishingServerId` 为 `central`，并启用 `autoPublish=true`。GitHub 仓库的 Actions Repository secrets 必须配置：

| Secret | 内容 |
| --- | --- |
| `CENTRAL_USERNAME` | Central Portal User Token 的用户名 |
| `CENTRAL_PASSWORD` | 同一组 User Token 的密码 |
| `MAVEN_GPG_PRIVATE_KEY` | 完整 ASCII armored 私钥，包括 BEGIN 和 END 行 |
| `MAVEN_GPG_PASSPHRASE` | 导出该私钥时对应的口令 |

Central 账户必须具有 `io.github.aut-rain` 命名空间的发布权限。公钥应已上传到 Central 支持的公共密钥服务器。

### 5.2 推荐的标签发布流程

完成评审与验证，将变更合入并推送 `main` 后，在对应提交上执行：

```powershell
git switch main
git pull --ff-only origin main
git status --short --branch
git log -1 --oneline
git tag --list v1.0.1
git ls-remote --tags origin refs/tags/v1.0.1
```

确认工作区干净、项目版本为 `1.0.1`、本地和远程标签均不存在，再执行：

```powershell
git tag -a v1.0.1 -m "release: v1.0.1"
git push origin v1.0.1
```

当前工作流不会自动修改 POM 版本，也没有自动校验标签与 POM 是否一致，发布前必须人工核对。标签 `v1.0.1` 必须对应 `<version>1.0.1</version>`。

### 5.3 手动发布与重试

进入 GitHub `Actions → Publish to Maven Central → Run workflow`，选择包含修复的 `main` 分支。触发前核对该分支的 POM 版本尚未发布。

- **只更新 Secrets，代码未变：** 可以在原任务中选择 `Re-run jobs`。
- **修改了工作流或 POM：** 提交并推送后，从工作流首页重新 `Run workflow`。旧任务的 `Re-run jobs` 仍使用旧提交。
- **Central 明确验证失败且版本未发布：** 修复后可以继续使用原版本号。
- **上传成功后发生超时或网络错误：** 先查 Central Deployments；可能仍在发布，不能直接认定失败并重复上传。
- **版本已经发布：** 不重复运行发布任务，后续修订使用新版本。

记录发布任务实际使用的 commit SHA。`1.0.0` 首次成功发布来自 `main` 的 `b371ff1`，早先创建的 `v1.0.0` 指向更早提交；追溯这次发布应以成功任务的 SHA 为准。后续版本使用通过验证的最终提交打标签，避免此类偏差，不强制移动既有标签。

## 6. 发布后确认与消费

1. 查看 Actions 日志，确认上传与验证结果。
2. 在 [Central Portal](https://central.sonatype.com/) 的 Deployments 中确认状态为 `PUBLISHED`。当前插件默认等待验证完成，Actions 绿色不单独等同于制品已同步到公共下载端点。
3. 检查 POM 下载地址，例如 [1.0.0 的 POM](https://repo.maven.apache.org/maven2/io/github/aut-rain/aut-rain-bom/1.0.0/aut-rain-bom-1.0.0.pom)。搜索索引和第三方镜像可能稍后才同步。
4. 使用没有预装该版本的 Maven 本地仓库进行消费验证，避免误把 `mvn install` 的本地文件当成远程发布成功的证据。

消费项目的配置：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.github.aut-rain</groupId>
            <artifactId>aut-rain-bom</artifactId>
            <version>1.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

使用方按需在 `dependencies` 中声明受管理依赖，省略版本号。导入新版本后重新检查依赖树并运行测试；其他项目不会因为 BOM 发布新版本而自动升级。

Maven 默认支持 Central，不需要下载凭据。如果使用方配置了全局镜像，则实际下载受镜像配置影响。短期找不到新版本时，先确认 Central 可下载，再检查镜像同步和 Maven 失败缓存，可在使用方执行 `mvn -U validate` 重试模型解析。

## 7. 常见故障排查

先展开 Actions 中标红的具体步骤，读取原始错误。Summary 中的 `exit code 1/2` 不能独立确定原因；清理失败也不能证明此前私钥导入成功。

| 错误或现象 | 排查与处理 |
| --- | --- |
| `gpg: no valid OpenPGP data found` | 检查私钥 Secret 是否存在、非空、名称一致；重新导出完整 ASCII armored 私钥，不能填路径、指纹或命令文本 |
| `Bad passphrase` | 检查 Secret 口令是否与导出的私钥匹配；本机改口令后需重新导出私钥，并同时更新两个 GPG Secrets |
| `No secret key` | 检查导入结果，确认包含可签名的私钥，而不是只有公钥或加密子密钥 |
| Central 返回 401 / 403 | 检查 User Token、命名空间权限及 `central` server ID；不要使用 GitHub 登录密码 |
| `Bundle has content that does NOT have a .pom file` | 旧发布插件与 Maven 3.10.0 的组合曾将本地元数据打入 bundle；当前已使用修复此问题的 `0.12.0`，若复现应检查实际插件版本和 bundle 文件列表 |
| 版本已存在 | 确认是否已经发布；已发布版本必须更换版本号 |
| Actions 成功但下载 404 | 检查 Deployments 是否已 `PUBLISHED`，再检查仓库同步与镜像延迟 |
| 修复后仍运行旧代码 | 对比任务 commit SHA；使用工作流首页的 `Run workflow` 启动新任务 |

当前 GPG 插件的 `passphrase` 配置会出现弃用警告；它与签名失败不是一回事。后续可迁移到插件支持的环境变量口令方式，并验证签名成功后再发布。不要把展开后的口令写入日志或文档。

## 8. 密钥维护与版本回退

- 定期检查 GPG 密钥有效期，提前续期并重新上传公钥；必要时重新导出私钥更新 Secret。
- 修改本机密钥口令不会自动更新 GitHub 中的私钥副本，需要同步更新私钥和口令两个 Secrets。
- 私钥、Token 和口令不进入 Git。私钥导出文件应放在仓库外，完成配置后妥善保管或移除临时副本。
- 发现凭据泄露时撤销受影响凭据并轮换；不要只删除文件或日志。
- 使用方升级失败时，先把 BOM 引用恢复到已验证的旧版本，再重新构建、测试和部署。
- 发布方为错误版本提供修订版本和变更说明，不通过覆盖旧制品实现回退。

## 9. 一次迭代的完成标准

- [ ] 依赖变化、升级原因和兼容范围已记录。
- [ ] Maven 模型检查和相关使用方验证完成。
- [ ] POM 版本、README 示例和发布记录一致。
- [ ] 标签与实际发布提交对应，Actions 使用预期提交。
- [ ] Central 显示 `PUBLISHED`，公共 POM 可下载。
- [ ] 使用方从远程仓库解析成功，已说明升级及回退方式。

参考：[Central 发布插件文档](https://central.sonatype.org/publish/publish-portal-maven/)、[Maven GPG 插件签名参数](https://maven.apache.org/plugins/maven-gpg-plugin/sign-mojo.html)。
